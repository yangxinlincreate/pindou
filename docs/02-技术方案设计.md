# 拼豆图纸平台 — 技术方案设计

> 版本：v1.0
> 日期：2026-11-07
> 对应 PRD：`01-产品需求文档-PRD.md`
> 首期形态：微信小程序（端侧计算）+ 轻量后端（账号/同步/数据下发）

---

## 1. 设计约束

在写任何代码前，先锁定四条不可动摇的约束，所有技术选型都必须服从：

| 编号 | 约束 | 原因 |
| --- | --- | --- |
| C1 | **原图不出端** | 隐私承诺，也是竞品宣传的核心卖点。所有像素处理在用户设备完成 |
| C2 | **配色结果必须落在可购色号集合内** | 产品的第一性。算法输出不是 RGB，而是 `colorId` |
| C3 | **端上生成耗时 P95 < 2s（48×48）** | 超过 3 秒用户会怀疑卡死 |
| C4 | **色号文字渲染不得拖垮主线程** | 10000 格逐格 `fillText` 是新手最容易踩的坑 |
| C5 | **首期零现金投入** | 无预算。不买服务器、不买域名、不买豆、不做微信认证 |

C1 与「服务端做图像算法」天然冲突；C5 更进一步，直接把服务端整个取消掉。因此：**算法完全端侧化，色卡数据随小程序包分发，首期不存在任何需要付费的基础设施。** 这两条共同决定了后面整套架构。

## 2. 技术选型

### 2.1 端侧

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 框架 | **微信原生小程序 + TypeScript** | 图像处理重度依赖 Canvas 2D 与 Worker，跨端框架（Taro/uni-app）在这一层封装薄、坑多，性能损耗不可控。首期只做小程序，原生最稳 |
| 渲染 | Skyline（渐进启用） | 编辑器滚动、手势更跟手。核心图纸区仍用 Canvas，不受影响 |
| 状态管理 | MobX（mobx-miniprogram） | 图纸状态（cells/palette）较大，需要响应式但不想手动 diff |
| 图像管线 | Canvas 2D（`type="2d"`）+ OffscreenCanvas | 拿到 ImageData 的唯一可靠路径 |
| 计算 | Web Worker（`wx.createWorker`）+ 主线程降级 | 量化算法不占主线程；Worker 不可用时主线程分片执行 |
| 本地存储 | 小程序 Storage（≤10MB）+ 文件系统 | 图纸 JSON 存 Storage，导出 PNG 存临时文件 |
| UI 组件 | 自研（不引 Vant/TDesign） | 色块与按钮需要严格控制颜色，第三方库的遮罩/滤镜会污染色准 |

### 2.2 服务端：首期不做

**这是 v1.1 最重要的架构变化。** v1.0 设计了一套 NestJS + PostgreSQL + Redis + COS 的后端，现在全部取消。

取消的依据不是「省事」，而是**算过账之后，首期确实不需要**：

| 常规需要后端的场景 | 首期是否需要 | 结论 |
| --- | --- | --- |
| 色卡数据下发 | 291 色 × 约 200 字节 ≈ 58 KB，gzip 后 12 KB | 打进分包 |
| LUT 下发 | 262 KB，gzip 后约 40 KB | 打进分包 |
| 用户登录 | 首期不需要账号，本地即用 | 不做 |
| 图纸存储 | 本地 Storage 存 20 张，每张 ≤ 60 KB | 够用 |
| 数据统计 | 微信小程序自带数据分析（免费） | 够用 |
| 内容审核 | 首期不做社区，无 UGC 上传 | 不需要 |

小程序主包限制 2 MB，分包总计 20 MB。色卡 + LUT 加起来 < 500 KB，**放在分包里绰绰有余**，而且加载速度比网络请求更快、更稳定（无网也能用）。

**唯一想做但做不了的**：图纸广场、云端同步、纠错数据回传。这三项全部推到 P2，等有后端再说。纠错数据先用微信客服会话收集（零开发、零成本）。

**Phase 2 的后端蓝图（现在不实现，仅存档）**：NestJS + PostgreSQL 16 + Redis + 腾讯云 COS。数据模型见 §7，API 见 §8。真到要上后端时，直接照这两章做即可。

### 2.3 数据流水线（离线，全部在本地跑）

零投入下的数据链路更短：

```
公开色卡数据（多源）
        ↓  抓取 + 清洗 + 交叉校验
   colors.json（含 confidence 标记）
        ↓
   ┌────┴────┐
   ↓         ↓
打进分包    构建 3D LUT（本地脚本）
(miniprogram/assets/colors/)    ↓
                      打进分包 (assets/lut/*.bin)
```

没有上传、没有 CDN、没有版本号下发。**更新色卡 = 改文件 + 重新提交审核 + 发版。** 发布频率低（色卡几个月才变一次），这个代价完全可以接受。

LUT 构建在本地跑一次（约 30 秒），产物直接提交进仓库。**不需要在 CI 里构建**——它是纯静态产物，产出稳定，没必要每次构建都跑。

## 3. 色彩科学基础

这一章是全项目的理论地基。所有「颜色是否接近」的判断都必须走这里定义的路径，**绝不允许出现直接用 RGB 欧氏距离比较颜色的代码**。

### 3.1 为什么不能用 RGB 距离

RGB 是设备相关的非线性空间。两个 RGB 值欧氏距离相等，人眼感知到的差异可能相差数倍——尤其在暗部和饱和区域。

例：`#000000` 与 `#1A1A1A` 的 RGB 距离是 26，`#FFFFFF` 与 `#E5E5E5` 也是 26，但前者几乎看不出差别，后者一眼能分辨。

拼豆场景下，这个误差直接表现为「图纸上看着渐变很顺，实际拼出来断层」，或「明明有更接近的色号，算法却选了另一个」。

### 3.2 转换链

统一走 **sRGB → Linear RGB → XYZ(D65) → CIELAB**，色差用 **CIEDE2000**。

```ts
// packages/color-core/src/space.ts

const D65 = { Xn: 0.95047, Yn: 1.0, Zn: 1.08883 };

/** sRGB 分量 (0-255) → 线性光 */
function srgbToLinear(c: number): number {
  const v = c / 255;
  return v <= 0.04045 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4);
}

export function rgbToXyz(r: number, g: number, b: number) {
  const R = srgbToLinear(r), G = srgbToLinear(g), B = srgbToLinear(b);
  return {
    X: 0.4124564 * R + 0.3575761 * G + 0.1804375 * B,
    Y: 0.2126729 * R + 0.7151522 * G + 0.0721750 * B,
    Z: 0.0193339 * R + 0.1191920 * G + 0.9503041 * B,
  };
}

const EPS = 216 / 24389;
const KAPPA = 24389 / 27;

function f(t: number): number {
  return t > EPS ? Math.cbrt(t) : (KAPPA * t + 16) / 116;
}

export function xyzToLab(X: number, Y: number, Z: number) {
  const fx = f(X / D65.Xn), fy = f(Y / D65.Yn), fz = f(Z / D65.Zn);
  return { L: 116 * fy - 16, a: 500 * (fx - fy), b: 200 * (fy - fz) };
}

export function rgbToLab(r: number, g: number, b: number) {
  const { X, Y, Z } = rgbToXyz(r, g, b);
  return xyzToLab(X, Y, Z);
}
```

### 3.3 CIEDE2000 实现

这是本项目最容易写错的一段代码，必须配单元测试（见 §11）。

```ts
// packages/color-core/src/deltaE.ts

const RAD = Math.PI / 180;
const DEG = 180 / Math.PI;
const POW25_7 = Math.pow(25, 7);

export function deltaE2000(
  L1: number, a1: number, b1: number,
  L2: number, a2: number, b2: number,
): number {
  const C1 = Math.hypot(a1, b1);
  const C2 = Math.hypot(a2, b2);
  const Cbar = (C1 + C2) / 2;
  const Cbar7 = Math.pow(Cbar, 7);
  const G = 0.5 * (1 - Math.sqrt(Cbar7 / (Cbar7 + POW25_7)));

  const a1p = (1 + G) * a1;
  const a2p = (1 + G) * a2;
  const C1p = Math.hypot(a1p, b1);
  const C2p = Math.hypot(a2p, b2);

  const h1p = C1p === 0 ? 0 : (Math.atan2(b1, a1p) * DEG + 360) % 360;
  const h2p = C2p === 0 ? 0 : (Math.atan2(b2, a2p) * DEG + 360) % 360;

  const dLp = L2 - L1;
  const dCp = C2p - C1p;

  let dhp = 0;
  if (C1p * C2p !== 0) {
    const diff = h2p - h1p;
    if (Math.abs(diff) <= 180) dhp = diff;
    else if (diff > 180) dhp = diff - 360;
    else dhp = diff + 360;
  }
  const dHp = 2 * Math.sqrt(C1p * C2p) * Math.sin((dhp * RAD) / 2);

  const Lbarp = (L1 + L2) / 2;
  const Cbarp = (C1p + C2p) / 2;

  let hbarp = h1p + h2p;
  if (C1p * C2p !== 0) {
    if (Math.abs(h1p - h2p) <= 180) hbarp = (h1p + h2p) / 2;
    else if (h1p + h2p < 360) hbarp = (h1p + h2p + 360) / 2;
    else hbarp = (h1p + h2p - 360) / 2;
  }

  const T =
    1 -
    0.17 * Math.cos((hbarp - 30) * RAD) +
    0.24 * Math.cos(2 * hbarp * RAD) +
    0.32 * Math.cos((3 * hbarp + 6) * RAD) -
    0.20 * Math.cos((4 * hbarp - 63) * RAD);

  const dTheta = 30 * Math.exp(-Math.pow((hbarp - 275) / 25, 2));
  const Cbarp7 = Math.pow(Cbarp, 7);
  const RC = 2 * Math.sqrt(Cbarp7 / (Cbarp7 + POW25_7));
  const SL = 1 + (0.015 * Math.pow(Lbarp - 50, 2)) / Math.sqrt(20 + Math.pow(Lbarp - 50, 2));
  const SC = 1 + 0.045 * Cbarp;
  const SH = 1 + 0.015 * Cbarp * T;
  const RT = -Math.sin(2 * dTheta * RAD) * RC;

  const tL = dLp / SL, tC = dCp / SC, tH = dHp / SH;
  return Math.sqrt(tL * tL + tC * tC + tH * tH + RT * tC * tH);
}
```

### 3.4 色差阈值的产品含义

| ΔE00 | 感知 | 产品处理 |
| --- | --- | --- |
| < 1.0 | 几乎无法分辨 | 视为同色，可合并 |
| 1.0 – 2.3 | 训练后可分辨 | 正常，不做提示 |
| 2.3 – 5.0 | 一眼能看出不同 | 跨品牌映射时标注「近似」 |
| 5.0 – 10 | 明显不同 | 禁止作为替代色，除非用户强制 |
| > 10 | 完全不同 | 绝不映射 |

**跨品牌等价色的阈值定为 ΔE00 ≤ 3.0**，超过则标注「无精确对应色」。

## 4. 核心算法：图片 → 色号图纸

### 4.1 整体流水线

```
原图 (任意尺寸)
  │
  ├─[1] 解码 + EXIF 方向修正
  ├─[2] 裁切（用户框选的区域）
  ├─[3] 背景处理（可选：合成到白底 / 抠图）
  ├─[4] 重采样到目标格数 W×H（面积平均，非最近邻）
  │
  ▼ 得到 W×H 的 RGB 矩阵（这就是最终的像素网格）
  │
  ├─[5] 转 Lab
  ├─[6] 调色板生成（K-means in Lab，K = 用户设定色数）
  ├─[7] 调色板 → 色卡映射（每个中心取 ΔE00 最近色号，去重）
  ├─[8] 逐格分配（在已选色号子集中取 ΔE00 最近）
  ├─[9] 后处理（孤立点清理 / 描边 / 边缘保护）
  ├─[10] 直方图统计 → 用量清单
  ▼
  pattern = { grid, palette[], cells: Uint8Array, stats }
```

关键设计决策：**第 4 步先降采样到目标格数，再做色彩量化。** 顺序反过来（先量化全图再缩放）会引入大量噪点，且计算量爆炸。

### 4.2 第 4 步：重采样必须用面积平均

```ts
/**
 * 面积平均重采样（box filter）。
 * 目标尺寸小于原图时，每个目标格 = 覆盖区域内所有源像素的加权平均。
 * 这能保留整体明暗关系，避免最近邻采样导致的锯齿和「丢细节」。
 */
function resampleBox(src: ImageData, dw: number, dh: number): Uint8ClampedArray {
  const { width: sw, height: sh, data } = src;
  const out = new Uint8ClampedArray(dw * dh * 4);
  const xRatio = sw / dw, yRatio = sh / dh;

  for (let dy = 0; dy < dh; dy++) {
    const y0 = Math.floor(dy * yRatio);
    const y1 = Math.min(sh, Math.ceil((dy + 1) * yRatio));
    for (let dx = 0; dx < dw; dx++) {
      const x0 = Math.floor(dx * xRatio);
      const x1 = Math.min(sw, Math.ceil((dx + 1) * xRatio));
      let r = 0, g = 0, b = 0, a = 0, n = 0;
      for (let y = y0; y < y1; y++) {
        let p = (y * sw + x0) * 4;
        for (let x = x0; x < x1; x++, p += 4) {
          r += data[p]; g += data[p + 1]; b += data[p + 2]; a += data[p + 3];
          n++;
        }
      }
      const o = (dy * dw + dx) * 4;
      out[o] = r / n; out[o + 1] = g / n; out[o + 2] = b / n; out[o + 3] = a / n;
    }
  }
  return out;
}
```

**要不要加锐化？** 加。降采样会软化边缘，而拼豆作品的辨识度极度依赖轮廓。在重采样后对亮度通道做一次轻量 unsharp mask（半径 1 格，强度 0.3–0.5），能显著改善小尺寸下五官的可辨认度。

### 4.3 第 6 步：Lab 空间 K-means 调色板

```ts
interface Centroid { L: number; a: number; b: number; }

/**
 * 加权 K-means（k-means++ 初始化）。
 * 权重来自像素重要性：肤色区域 ×2.0，边缘区域 ×1.5，其余 ×1.0。
 */
function kmeansPalette(
  labs: Float32Array,   // 长度 = n*3
  weights: Float32Array,
  k: number,
  maxIter = 24,
): Centroid[] {
  const n = weights.length;
  const centers = kmeansPlusPlusInit(labs, weights, k);

  const assign = new Int32Array(n);
  for (let iter = 0; iter < maxIter; iter++) {
    let changed = 0;
    // 分配
    for (let i = 0; i < n; i++) {
      const L = labs[i * 3], a = labs[i * 3 + 1], b = labs[i * 3 + 2];
      let best = 0, bestD = Infinity;
      for (let c = 0; c < k; c++) {
        const dL = L - centers[c].L, da = a - centers[c].a, db = b - centers[c].b;
        const d = dL * dL + da * da + db * db;  // Lab 欧氏，够快，且可用于聚类
        if (d < bestD) { bestD = d; best = c; }
      }
      if (assign[i] !== best) { assign[i] = best; changed++; }
    }
    // 更新（加权质心）
    const sum = new Float64Array(k * 3);
    const wsum = new Float64Array(k);
    for (let i = 0; i < n; i++) {
      const c = assign[i], w = weights[i];
      sum[c * 3] += labs[i * 3] * w;
      sum[c * 3 + 1] += labs[i * 3 + 1] * w;
      sum[c * 3 + 2] += labs[i * 3 + 2] * w;
      wsum[c] += w;
    }
    for (let c = 0; c < k; c++) {
      if (wsum[c] > 0) {
        centers[c] = {
          L: sum[c * 3] / wsum[c],
          a: sum[c * 3 + 1] / wsum[c],
          b: sum[c * 3 + 2] / wsum[c],
        };
      }
    }
    if (changed / n < 0.01) break;  // 收敛
  }
  return centers;
}
```

**聚类用 Lab 欧氏距离，最终匹配用 ΔE00。** 这是有意的：K-means 迭代几十万次，ΔE00 太贵；聚类本身只需要大致合理的分组，欧氏在 Lab 空间已经比 RGB 好得多。最终落色号的精度由 ΔE00 保证。

**权重设计的实际效果**：

| 区域 | 权重 | 目的 |
| --- | --- | --- |
| 肤色（YCbCr 检测） | 2.0 | 人像的脸不能偏色、不能糊 |
| 边缘（Sobel 梯度 top 30%） | 1.5 | 保住轮廓和五官 |
| 其余 | 1.0 | 背景不应吃掉色数预算 |

**肤色检测（YCbCr 简化版）**：

```ts
function isSkin(r: number, g: number, b: number): boolean {
  const y  =  0.299 * r + 0.587 * g + 0.114 * b;
  const cb = -0.169 * r - 0.331 * g + 0.500 * b + 128;
  const cr =  0.500 * r - 0.419 * g - 0.081 * b + 128;
  return y > 60 && cb >= 77 && cb <= 127 && cr >= 133 && cr <= 173;
}
```

不追求精确，只求覆盖。误判带来的副作用（非肤色区域权重略高）远小于漏判。

### 4.4 第 7 步：调色板 → 色卡映射

```ts
interface MappedColor {
  colorId: string;   // 'mard:A1'
  code: string;      // 'A1'
  hex: string;       // '#FFFFFF'
  lab: [number, number, number];
  deltaE: number;    // 与聚类中心的偏差，用于质量预警
}

function mapCentroidsToPalette(
  centers: Centroid[],
  available: ColorLab[],   // 当前品牌/套装允许的色号
  mergeThreshold = 1.0,    // ΔE00 < 1 视为同色，合并
): MappedColor[] {
  const picked: MappedColor[] = [];

  for (const c of centers) {
    let best: ColorLab | null = null;
    let bestD = Infinity;
    for (const col of available) {
      const d = deltaE2000(c.L, c.a, c.b, col.L, col.a, col.b);
      if (d < bestD) { bestD = d; best = col; }
    }
    if (!best) continue;

    // 去重：两个聚类中心可能落到同一个色号
    const exist = picked.find((p) => p.colorId === best!.id);
    if (exist) {
      if (bestD < exist.deltaE) exist.deltaE = bestD;
      continue;
    }
    picked.push({
      colorId: best.id, code: best.code, hex: best.hex,
      lab: [best.L, best.a, best.b], deltaE: bestD,
    });
  }

  // 二次合并：色卡里两个颜色本身太接近（ΔE<mergeThreshold）时保留用量大的
  return mergeSimilar(picked, mergeThreshold);
}
```

**重要**：`picked.length` 可能小于用户设定的 K。这是正常的——用户要 32 色，但照片实际只有 24 种明显色调，硬凑会引入肉眼无差别的色号，反而增加分拣成本。界面上应显示实际色数：「已用 24 色（目标 32）」。

### 4.5 第 8 步：逐格分配（性能核心）

朴素实现是每个像素遍历全部色号算 ΔE00。48×48=2304 格 × 291 色 = 67 万次，可接受。但 200×200 = 4 万格 × 291 色 = 1164 万次 ΔE00，约 4–8 秒，不可接受。

**方案：3D LUT 查表。**

离线构建一个 32×32×32 的 RGB 查找表，每个格点存储色卡中最接近的 top-4 色号索引。运行时逐格查表，再对 4 个候选算精确 ΔE00。

```
LUT 尺寸 = 32³ × 4 × 2 字节 = 262,144 字节 = 256 KB
gzip 后约 35–45 KB（颜色分布连续，压缩率高）
```

```ts
// 离线构建脚本：scripts/build-lut.ts
const N = 32;             // 每通道格数
const TOP_K = 4;

function buildLut(palette: ColorLab[]): Uint16Array {
  const lut = new Uint16Array(N * N * N * TOP_K);
  for (let ri = 0; ri < N; ri++) {
    for (let gi = 0; gi < N; gi++) {
      for (let bi = 0; bi < N; bi++) {
        const r = Math.round((ri / (N - 1)) * 255);
        const g = Math.round((gi / (N - 1)) * 255);
        const b = Math.round((bi / (N - 1)) * 255);
        const { L, a, bb } = rgbToLab(r, g, b);  // 注意命名冲突，实际用 lab.b

        // 全量算 ΔE00，取 top K
        const scored = palette.map((c, i) => ({
          i,
          d: deltaE2000(L, a, bb, c.L, c.a, c.b),
        }));
        scored.sort((x, y) => x.d - y.d);

        const base = ((ri * N + gi) * N + bi) * TOP_K;
        for (let k = 0; k < TOP_K; k++) {
          lut[base + k] = scored[k]?.i ?? 0;
        }
      }
    }
  }
  return lut;
}
```

运行时：

```ts
function lookupNearest(
  r: number, g: number, b: number,
  lut: Uint16Array, palette: ColorLab[],
): number {
  const ri = Math.min(N - 1, (r * (N - 1) / 255) | 0);
  const gi = Math.min(N - 1, (g * (N - 1) / 255) | 0);
  const bi = Math.min(N - 1, (b * (N - 1) / 255) | 0);
  const base = ((ri * N + gi) * N + bi) * TOP_K;

  const { L, a, bb } = rgbToLab(r, g, b);
  let best = lut[base], bestD = Infinity;
  for (let k = 0; k < TOP_K; k++) {
    const idx = lut[base + k];
    const c = palette[idx];
    const d = deltaE2000(L, a, bb, c.L, c.a, c.b);
    if (d < bestD) { bestD = d; best = idx; }
  }
  return best;
}
```

性能对比（48×48 格，iPhone 12 / 骁龙 778G 实测估算）：

| 方案 | ΔE00 调用次数 | 预计耗时 |
| --- | --- | --- |
| 全量遍历 291 色 | 67 万 | 280 ms |
| LUT + top4 | 9,216 | 4 ms + 查表 |

200×200 时差距从「秒级」拉平到「几十毫秒」。**LUT 是必做项，不是优化项。**

**LUT 的精度问题**：32³ 网格意味着每个格点代表 8×8×8 的 RGB 立方体，格点颜色与实际像素可能差 4 个 RGB 值。但因为 top-4 候选保留了多样性，且最终用 ΔE00 精确比对，实际误差可忽略。

**边界情况**：如果某个格点的 top-4 恰好全不是最优（概率极低但存在），会选到次优色。可通过增大 TOP_K=6 缓解，代价是 LUT 384KB（gzip 后 55KB）。**建议 TOP_K=4，并在验收时用 1000 张测试图对比「LUT 结果」与「全量结果」的一致率，要求 > 99.5%。**

### 4.6 第 8 步补充：抖动（Dithering）

拼豆作品要不要抖动，是个产品判断，不是技术判断。

- **开启**：色彩过渡自然，渐变好看。但会产生大量孤立单颗杂色，摆豆时极其痛苦，且实际观感因为豆子是独立圆点，噪声感更强。
- **关闭**：色块干净，好摆。但不做渐变，天空、肤色过渡会出现断层。

**决策：默认关闭，作为高级选项提供，并在选项旁注明「会显著增加摆豆难度」。** 提供 Atkinson 抖动（比 Floyd-Steinberg 噪声更规整，适合像素艺术）而非 FS。

### 4.7 第 9 步：后处理

#### 孤立点清理

单个格子与周围 8 个邻居颜色完全不同（且该色在全局用量极少），基本是噪点，替换为邻居中占比最高的颜色。

```ts
function despeckle(cells: Uint8Array, w: number, h: number, minIsland = 2): void {
  const src = cells.slice();
  for (let y = 0; y < h; y++) {
    for (let x = 0; x < w; x++) {
      const i = y * w + x;
      const c = src[i];
      const same = neighbors8(x, y, w, h).filter((n) => src[n] === c).length;
      if (same === 0) {
        const counts = new Map<number, number>();
        for (const n of neighbors8(x, y, w, h)) {
          counts.set(src[n], (counts.get(src[n]) ?? 0) + 1);
        }
        const top = [...counts.entries()].sort((a, b) => b[1] - a[1])[0];
        if (top && top[1] >= minIsland) cells[i] = top[0];
      }
    }
  }
}
```

注意：**只清理「周围没有任何同色邻居」的孤立点**，不要用更大的连通域判断——会把眼睛高光、小logo这类有意义的单点细节一起删掉。

#### 描边（可选，P1）

拼豆作品常见的卡通化手法。实现：对 Alpha/亮度通道做 Sobel，梯度超过阈值的格子替换为描边色（默认取全图最深的色号，或让用户指定）。

#### 边缘保护

在 K-means 权重里已经处理（边缘 ×1.5）。另外可在后处理阶段做一次「轮廓色加深」：检测到边缘且亮度高于邻域均值的格子，向浅一档色号替换，增强立体感。**这一步默认关闭，作为 Pro 选项。**

### 4.8 第 10 步：用量统计与分板

interface PatternStats {

### 4.9 直接导入：不经过主流水线的第二条路径

前面 §4.1–§4.8 是**照片模式**。**直接导入是独立路径，不走那条流水线。**

原因很简单：照片模式的所有设计（面积平均、K-means、去噪、锐化）都建立在「原图是连续色调、需要压缩到有限色数」这个前提上。而像素图恰好相反——**色数本来就不多，边缘本来就是硬的，每一个小点都是作者刻意放的。**

对像素图做任何"优化"，都是在毁作品。

#### 4.9.1 两条路径的差异总表

| 步骤 | 照片模式 | 直接导入 |
| --- | --- | --- |
| 重采样 | 面积平均 + 锐化 | **最近邻**，绝不平均 |
| 调色板 | K-means 聚类到用户设定色数 | **保留原色数**，仅超容量时合并 |
| 落色号 | LUT 查表 + ΔE00 | 逐色 ΔE00（色数少，无需 LUT） |
| 去噪 | 孤立点清理 | **不做** |
| 抖动 | 默认关 | **强制关** |
| 描边 | 可选 | **不做** |
| 相近色合并 | 是（ΔE<1 合并） | **不合并** |
| 格数 | 用户自由设定 | 由原图格子边长推导 |
| 透明通道 | 合成到白底 | **透明 = 空格，不摆豆** |

**这张表要贴在代码里。** 后来接手的人最容易做的事就是"顺手给导入模式加个锐化"，然后作品就废了。

#### 4.9.2 格子边长识别

```ts
/**
 * 检测像素图中每个「逻辑像素」占多少物理像素。
 * 返回 null 表示识别失败，需用户手动指定格数。
 */
function detectGridSize(img: ImageData): number | null {
  const { width: w, height: h, data } = img;

  const hist = new Map<number, number>();   // 间距 → 出现次数

  // 横向扫描：找颜色跳变点，统计跳变间距
  for (let y = 0; y < h; y++) {
    let runStart = 0;
    let prev = px(data, w, 0, y);
    for (let x = 1; x < w; x++) {
      const cur = px(data, w, x, y);
      if (cur !== prev) {
        const run = x - runStart;
        if (run >= 2) hist.set(run, (hist.get(run) ?? 0) + 1);
        runStart = x;
        prev = cur;
      }
    }
  }
  if (hist.size === 0) return 1;  // 全图同色，或已经是 1 像素 = 1 格

  // 取出现次数最多的间距
  const [g] = [...hist.entries()].sort((a, b) => b[1] - a[1])[0];

  // 校验：必须能整除图宽/图高（允许 ±1 的取整误差）
  const okW = w % g === 0 || Math.abs((w % g) - g) <= 1;
  const okH = h % g === 0 || Math.abs((h % g) - g) <= 1;
  if (!okW || !okH) return null;

  // 统计意义上太弱（多数间距都不等于 g）则判失败
  const total = [...hist.values()].reduce((a, b) => a + b, 0);
  const confidence = (hist.get(g) ?? 0) / total;
  return confidence >= 0.5 ? g : null;
}
```

**为什么会失败**：作者可能用了非整数倍缩放、导出时开了抗锯齿、或被微信压缩过。失败时不要硬猜，直接让用户输入格数——用户自己画的图，他知道是多少格。

#### 4.9.3 采样与配色

```ts
function importPixelArt(
  img: ImageData, gridSize: number, palette: ColorLab[],
): { w: number; h: number; cells: Uint8Array; palette: ColorLab[] } {
  const g = gridSize;
  const w = Math.floor(img.width / g);
  const h = Math.floor(img.height / g);

  // 偏移居中：原图尺寸不是 g 的整数倍时，从中心对齐裁切，不拉伸
  const ox = Math.floor((img.width - w * g) / 2);
  const oy = Math.floor((img.height - h * g) / 2);

  const cells = new Uint8Array(w * h);
  const colorCache = new Map<number, number>();  // 原色 RGB → 色卡索引

  for (let y = 0; y < h; y++) {
    for (let x = 0; x < w; x++) {
      // 取格子中心像素，不做平均
      const sx = ox + x * g + (g >> 1);
      const sy = oy + y * g + (g >> 1);
      const [r, gg, b, a] = readPx(img, sx, sy);

      // 透明 → 空格（255）
      if (a < 128) { cells[y * w + x] = 255; continue; }

      const key = (r << 16) | (gg << 8) | b;
      let idx = colorCache.get(key);
      if (idx === undefined) {
        idx = nearestColorIndex(r, gg, b, palette);  // ΔE00
        colorCache.set(key, idx);
      }
      cells[y * w + x] = idx;
    }
  }
  return { w, h, cells, palette };
}
```

**`cells` 用 255 表示空格**（不摆豆）。调色板最多 255 色，够用。照片模式复用同一个数据结构，只是不会产生 255。

#### 4.9.4 原色数超过色卡容量时

像素图可能用了 80 种颜色，而色卡只有 291 色——通常够。但如果用户选了套装（72 色），就会超。

处理顺序：

1. 统计每个原色（映射后的色号）的实际用量
2. 按用量降序
3. 保留前 N 个（N = 色卡可用色数）
4. 剩余的原色，各自映射到「已保留色号中 ΔE00 最小者」
5. **在界面上明确告知**：「原图 80 色，已合并为 72 色，其中 12 种颜色被替换为最接近色」

**不要静默合并。** 像素画作者对颜色极其敏感，悄悄改他的图是最大的冒犯。

#### 4.9.5 抗锯齿检测

有些"像素风"图片其实是插画缩小后带抗锯齿的，强行 1:1 导入会得到一堆边缘杂色。

检测方法：统计所有映射后色号，若存在大量「用量 < 总格数 1% 且只出现在色块边界」的色号，则提示：

> 这张图似乎有抗锯齿，直接导入可能产生杂色。建议改用照片模式。

给用户两个按钮：「仍要导入」/「改用照片模式」。不强制。

#### 4.9.6 边界情况

| 情况 | 处理 |
| --- | --- |
| 透明 PNG | 透明格 = 空格，不摆豆；用量清单不计入 |
| 半透明（alpha 0.1–0.9） | 按 alpha ≥ 0.5 视为不透明，否则空格。不合成背景 |
| 图宽/高不是 g 的整数倍 | 中心对齐裁切，不缩放 |
| 1 像素 = 1 格 | g = 1，直接逐像素 |
| 图片过大（> 4096） | 先按最近邻降采样到 4096 以内（仍是整数倍关系） |
| 检测到 g 但格数 > 200 | 提示「格数超出上限，建议照片模式或裁切图片」 |

## 6. 系统架构

### 6.1 部署拓扑：没有拓扑

首期架构就是一句话：**一个装了数据的封闭小程序，不联网也能跑。**

```
┌─────────────────────────────────────────┐
│  微信小程序                              │
│                                          │
│  主包 (< 2 MB)                           │
│   ├─ 页面、组件、core/ 算法               │
│   └─ 启动即用                            │
│                                          │
│  分包 assets (< 500 KB)                  │
│   ├─ colors/mard-221.json    (12 KB gz)  │
│   ├─ colors/coco-291.json    (12 KB gz)  │
│   └─ lut/mard-221.bin        (40 KB gz)  │
│                                          │
│  本地 Storage                            │
│   └─ 最近 20 张图纸                       │
└─────────────────────────────────────────┘

              （无服务器、无域名、无数据库）
```

**为什么数据要放分包而不是主包**：色卡和 LUT 只在「生成」时才用到，不需要在冷启动时加载。分包在进入做图页时下载/加载即可，主包保持精简，启动更快。

**首次加载后无需再联网。** 这是零投入带来的一个意外优势——竞品每次都要请求色卡接口，我们连网都不用，弱网环境体验反而更好。

### 6.3 Worker 边界

Worker 不能访问 Canvas。因此：

```
主线程                              Worker
  │
  ├─ Canvas 解码图片
  ├─ getImageData → Uint8ClampedArray
  ├────────── transfer ─────────→
  │                                 ├─ resample
  │                                 ├─ Lab 转换
  │                                 ├─ K-means
  │                                 ├─ LUT 查表分配
  │                                 ├─ despeckle
  │                                 └─ 统计
  │←───────── transfer ────────────┤
  ├─ 绘制图纸
```

Worker 里需要 LUT 数据。方案：主线程从**分包**读取 LUT 文件（`wx.getFileSystemManager().readFileSync` 或 `require` 分包资源），通过 `worker.postMessage({ lut: buffer })` 传一次（`transferable`，零拷贝），Worker 内部缓存。整个过程不涉及网络。

**注意**：小程序 Worker 的文件系统 API 与主线程不完全一致，分包内的二进制资源建议由主线程读取后传入，不要在 Worker 里直接 readFile。这个坑在真机上才会暴露，模拟器正常。


**Worker 不可用的降级**：用 `requestIdleCallback` 分片执行，每 200ms 让出主线程一次，显示进度条。降级路径必须实现，因为部分低端机或小程序基础库版本不支持 Worker。

### 6.4 图纸渲染（性能关键）

100×100 = 10000 格，每格一次 `fillRect` + 一次 `fillText`，必崩。

三层优化：

1. **视口裁剪**：只绘制视口内的格子。放大到 4x 时，屏幕上只有约 300 格，绘制量恒定。
2. **色号文字图集**：所有可能出现的色号字符串（最多 300 个）预渲染到一张离屏 Canvas 图集，绘制时用 `drawImage` 切片，而不是 `fillText`。`fillText` 单次约 20–50μs，10000 次就是 0.2–0.5 秒；`drawImage` 单次约 2μs。
3. **缩放阈值**：格宽 < 10px 时不画文字，只画色块；< 4px 时不画网格线。

```ts
// 伪代码：渲染循环
function render(ctx, viewport, pattern, scale) {
  const { x0, y0, x1, y1 } = visibleCells(viewport, scale);
  const cellPx = pattern.cellSize * scale;

  for (let y = y0; y <= y1; y++) {
    for (let x = x0; x <= x1; x++) {
      const color = pattern.palette[pattern.cells[y * pattern.w + x]];
      const px = (x - x0) * cellPx, py = (y - y0) * cellPx;

      if (renderMode === 'bead') drawBead(ctx, px, py, cellPx, color.hex);
      else { ctx.fillStyle = color.hex; ctx.fillRect(px, py, cellPx, cellPx); }

      if (cellPx >= 10) drawCode(ctx, atlas, color.code, px, py, cellPx);
      if (cellPx >= 4) strokeGrid(ctx, px, py, cellPx);
    }
  }
}
```

### 6.5 Web 管理后台（数据工作台）

后台不是"小程序的另一半"，它是一条**离线数据生产线**的工位。理解这一点，技术选型就没什么可纠结的。

**选型**：

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 构建 | Vite + React 18 + TypeScript | 13 个菜单项、P0 只落地 6 个页面，不需要更重的东西 |
| 存储 | Dexie（IndexedDB） | 221 个色号 + 编辑历史，localStorage 装不下也不该装 |
| UI | 手写 CSS，不引组件库 | 色块必须显示真实色值，组件库的遮罩/主题色会污染判断 |
| 色彩 | 复用 `packages/color-core` | **必须复用**，理由见下 |
| 算法 | 复用 `packages/algo` 的 LUT 构建 | 同一份实现，避免两套代码算出不同结果 |
| 部署 | 本地 `vite dev`，可选 GitHub Pages | 不需要公网，不需要登录 |

**为什么色彩计算必须复用同一个包**：如果后台自己实现一遍 Lab 转换，浮点细节稍有不同，就会出现「后台看着是这个色，端上配色选了另一个色号」——这类 bug 排查成本极高，而且只在特定色号上偶发。共用 D 包是唯一可靠的做法。

**数据流**：

```
多源 CSV（data/sources/）
        ↓ 导入
   IndexedDB（浏览器本地）
        ↓ 人工裁决 / 编辑 / 校验
   data/mard-221.csv（导出，进仓库）
        ↓
   ┌────┴─────┐
   ↓          ↓
colors.json  LUT .bin
   ↓          ↓
miniprogram/assets/colors/ 、 /lut/
        ↓
     重新提审发版
```

**数据契约**：后台导出的 JSON 必须与 §7.2 的结构完全一致，用 `packages/shared` 里的类型定义强制约束。后台不做"自己的一套格式再转换"——那必然会产生字段漂移。

**菜单画全，实现分阶段**：侧边栏 13 项一次性画出来（灰色项就是路线图），P0 只落地 7 个纯前端页面：仪表盘、色卡管理、数据校验、套装配置、LUT 构建、版本发布、设置。用户管理、图纸管理、纠错工单、内容审核、订单都依赖后端，等 Phase 2 再补。

**但有一个例外值得早做**：纠错工单。它首期可以只做一个"粘贴客服会话记录"的表单，人工把用户反馈的色号与颜色填进去，攒到 3 条就去改数据。这个工具不需要后端，却能直接提升色卡准确度——而色卡准确度是长期唯一的护城河。

**一个容易忽略的点**：后台的散点图用纯 SVG 画（`.map` 生成 `<circle>`），不要引 ECharts / D3。221 个点，SVG 足够，而且省掉 300KB 依赖。

### 7.2 首期实际存储（这是真正要实现的部分）

**色卡**：编译期打进分包的静态 JSON，结构直接对应 §5.2 的 `ColorRecord`：

```jsonc
// assets/colors/mard-221.json
{
  "seriesId": "mard-221",
  "brandName": "MARD",
  "beadSize": 5.0,
  "version": "2026.11.1",
  "source": "public-crossref",          // 向用户披露数据来源
  "colors": [
    { "id": "mard-221:A1", "code": "A1", "name": "白色", "hex": "#FFFFFF",
      "lab": [100, 0, 0], "finish": "solid", "confidence": "public" }
  ],
  "sets": [
    { "id": "mard-set-72", "name": "72 色套装", "codes": ["A1", "..."] }
  ]
}
```

**图纸**：本地 Storage，key 前缀 `pattern:`，索引单独存一条：

```ts
// Storage: 'pattern:index' → 最近 20 条的轻量索引
interface PatternIndexItem {
  id: string;
  title: string;
  seriesId: string;
  w: number; h: number;
  colorCount: number;
  totalBeads: number;
  thumb: string;      // 本地临时文件路径，不是 base64（base64 会把 Storage 撑爆）
  createdAt: number;
}

// Storage: 'pattern:{id}' → 完整图纸
interface StoredPattern {
  version: 1;
  seriesId: string;
  w: number; h: number;
  beadSize: number;
  mode: 'photo' | 'import';
  cells: string;      // base64 of Uint8Array，48×48 约 3 KB
  palette: { colorId: string; code: string; hex: string; count: number }[];
}
```

**容量核算**：小程序 Storage 上限 10 MB。单张 100×100 图纸 `cells` 为 10000 字节 → base64 约 13.6 KB，加调色板与元数据约 15 KB。存 20 张 ≈ 300 KB，**远低于上限**。

真正的风险不是图纸，而是**缩略图**。如果缩略图用 base64 存 Storage，一张 200×200 的 PNG 可能就 50 KB，20 张就 1 MB，且读写极慢。**缩略图必须存成本地临时文件**（`wx.getFileSystemManager().saveFile`），Storage 里只存路径。

> 本地临时文件会被微信清理（`saveFile` 保存的文件不会自动清理，但 `tempFilePath` 会）。导出图请务必用 `saveFile` 转成持久文件，否则用户第二天打开历史记录全是白图。

## 9. 性能预算

| 环节 | 预算（48×48） | 预算（200×200） |
| --- | --- | --- |
| 图片解码 | 80 ms | 80 ms |
| 重采样 | 20 ms | 15 ms |
| Lab 转换 | 5 ms | 40 ms |
| K-means（24 iter, K=32） | 120 ms | 1,800 ms |
| LUT 分配 | 8 ms | 60 ms |
| 后处理 | 5 ms | 40 ms |
| 首屏渲染 | 30 ms | 30 ms（视口裁剪） |
| **合计** | **~270 ms** | **~2,100 ms** |

K-means 是唯一可能超标的环节。优化手段（按优先级）：

1. **降采样聚类**：格数 > 10000 时，先用 1/2 采样做聚类，得到中心后再对全量分配。误差极小，速度 ×4。
2. **k-means++ 初始化**代替随机初始化，减少迭代次数（通常 8–12 次即收敛）。
3. **提前终止**：中心位移 < 0.5 即停止。
4. 极端情况（200×200 + 48 色）在主线程分片，显示进度条。

## 10. 合规与安全

### 10.1 小程序类目

- 主类目：**工具 → 图片处理**
- 若上线图纸广场（P2），需增加 **社交 → 社区/论坛**，并配置内容审核

**个人主体的类目风险（首周必须验证）**：

个人可选类目少于企业，`工具 → 图片处理` 是否对个人开放需要实际注册后验证。这不是理论风险，而是决定整个项目能否落地的关键分叉：

| 验证结果 | 走法 |
| --- | --- |
| 可选「工具 → 图片处理」 | 按本文档正常推进 |
| 类目被拒 | **转 H5**：`packages/color-core` 与 `packages/algo` 是纯 TS、零平台依赖，换成浏览器 Canvas 只需要改图像读取层（`createImageBitmap` + `OffscreenCanvas`），算法一行不用动。托管用免费静态服务（Vercel / Cloudflare Pages / GitHub Pages），仍然 ¥0 |

**这就是把算法写成纯函数、与平台解耦的原因。** 如果一开始把算法写死在小程序 API 里，类目被拒时就得整个重写。

建议：注册后第一天就去选类目，别等代码写完。

### 10.2 内容安全

**零后端带来一个意外的好处：内容安全风险几乎归零。**

平台要求做内容检测，针对的是「用户内容回流到服务器、可能被其他用户看到」。而首期：

- 原图不上传（架构上做不到）
- 生成的图纸不出手机
- 分享是用户主动把图发给自己好友，走微信原生聊天，由微信自身风控兜底
- **没有任何 UGC 进入公共可见范围**

因此首期**不需要接入 `msgSecCheck` / `imgSecCheck` / `mediaCheckAsync`**，也用不了（那几个接口都需要自有服务端）。

**但这个结论有一个前提：不做图纸广场。** 一旦上线公开分享（P2），就必须补：
- 服务端 + `mediaCheckAsync` 异步检测（需配置回调与 `msg_signature` 校验）
- `imgSecCheck` 同步检测（1 MB / 750 px 限制，需先压缩）
- 人工抽审

**把这条写进 P2 的准入条件，别忘。** 无审核的公开图片社区，是小程序被封最快的路径。

### 10.3 隐私合规

必须在小程序内配置《用户隐私保护指引》，声明：

- 收集的信息：相册读取权限（仅本地读取原图）、相册写入权限（保存导出图）
- **不收集任何个人信息**：首期无登录、无手机号、无位置、无设备标识
- 图片处理位置：本地，不上传
- 无云端保存（Phase 2 若有，须用户主动点击才上传，并明确告知）

`app.json` 中声明 `permission.scope.writePhotosAlbum`、`scope.camera` 用途说明。**因为没有后端，隐私政策可以写得非常干净——这一条在审核时是加分项。**

### 10.4 数据权属

- **色值（HEX/Lab）属于事实性数据，不受著作权保护。** 颜色本身是自然存在的，我们记录的是「某个色号大概是什么颜色」这个事实。
- **品牌名称、Logo 是商标。** 仅用于兼容性说明，页面须标注：「色号与色值仅为选购参考，非品牌官方数据，实物以品牌色卡为准。」
- **只取色值，不搬图片和文案。** 从公开站点获取数据时，只提取数字（色号 → HEX），不复制其页面设计、描述文字、色卡图片。低频访问，遵守 robots.txt。
- **首期数据来源要在「关于」页如实披露**，写清是「综合公开资料整理，非官方测量值」。这句坦白会损失一点信任，但比用户自己发现后不信任要好得多。
- 《生成式 AI 服务管理暂行办法》不适用（不提供 AI 生成图像）。

### 10.5 数据安全

- 用户原图不落盘、不上传，端侧处理即释放内存
- 所有图纸仅存本机 Storage，卸载小程序即清除
- 无接口，因此无接口限流、无越权、无拖库风险
- **唯一的对外通道是客服会话**，用户主动发起，你只能看到用户主动发的内容

## 11. 测试策略

### 11.1 算法正确性

| 测试 | 方法 | 通过标准 |
| --- | --- | --- |
| ΔE00 实现 | 用 Sharma 等人的 34 组标准测试数据（CIEDE2000 test data） | 全部误差 < 1e-4 |
| Lab 转换 | 已知 RGB → Lab 对照表（如 #FF0000 → L=53.24, a=80.09, b=67.20） | 误差 < 0.01 |
| K-means 收敛 | 随机数据 + 固定种子，验证不变量（单调不增的距离和） | 通过 |
| LUT 一致性 | 1000 张测试图，对比 LUT 结果与全量 ΔE00 结果 | 一致率 > 99.5% |
| 套装约束 | 生成结果所有 colorId ∈ 套装集合 | 100% |
| 直接导入还原度 | 取 32×32 像素图，放大 8 倍（最近邻）后导入，比对结果与原始像素图 | **逐格 100% 一致** |
| 格子尺寸识别 | 20 张不同放大倍数（2/3/4/6/8/10 倍）的像素图 | 识别成功率 100%，误判 0 |
| 透明通道 | 带透明背景的 PNG 导入 | 透明格为空格，不计入用量 |
| 抗锯齿检测 | 带抗锯齿的假像素图 | 正确提示，不误报真像素图 |

Sharma 测试数据是 CIEDE2000 的黄金标准，务必用上——手写实现里 `hbarp` 的边界处理、`RT` 的符号极易出错，肉眼看不出来但结果差几个 ΔE。

### 11.2 性能测试

固定 20 张样本图（含人像、风景、卡通、纯色、渐变、高对比），在 5 台设备上跑（低端安卓 / 中端安卓 / iPhone SE / iPhone 12 / iPhone 15），记录 P50/P95 耗时。

### 11.3 视觉验收

**必须在真实手机上对照实物豆看，不能只看屏幕。** 验收方法：

1. 打印图纸（300 DPI）
2. 按图纸摆豆、熨烫
3. 与原图并排拍照对比
4. 由「色差是否可接受」决定是否调整算法参数

这一步不能省。屏幕上看完美的配色，实际拼出来可能偏色明显。

| **S5 预览与导出** | 1 周 | 预览、分板线、烫后视角、用量清单、导出分享 | 烫后视角可砍 |
| **S6 联调验收** | 1 周 | 真机测试、性能优化、视觉对照 | 需要真机若干台 |
| **S7 提审上线** | 3–5 天 | 隐私协议、类目材料、提审、灰度 | 审核可能打回，留余量 |
| **合计** | **约 7 周** | MVP 上线 | 比 v1.0 少 4.5 周 |

**省下来的时间来自三处**：砍掉后端（-1.5 周）、色卡不实拍（-1.5 周）、不需要登录与账号体系（-1 周）。代价是色卡精度，这个代价是明账，认了。

**新增的时间**：直接导入（+0.6 周）。这是首期的差异化卖点，值得。

**排期风险**：S4 的 Canvas 渲染最容易被低估。10000 格的视口裁剪 + 文字图集，第一次写通常要返工两轮。给自己留缓冲。

## 13. 关键技术风险

| 风险 | 概率 | 影响 | 预案 |
| --- | --- | --- | --- |
| **个人主体类目被拒** | 中 | 致命 | S0 第一天验证；算法与平台解耦，转 H5 只需改图像读取层 |
| **公开色卡数据不准** | 高 | 高 | 多源交叉取中位数；界面披露；客服会话收集纠错；不承诺绝对准确 |
| 小程序 Canvas 2D 在低端机 `getImageData` 极慢 | 中 | 高 | 限制最大输入尺寸（长边 2048），超出先降采样；实测后确定阈值 |
| Worker 传递大 ArrayBuffer 卡顿 | 中 | 中 | 分块传输；或改为主线程分片 |
| LUT 与全量结果差异超预期 | 低 | 中 | 提高 TOP_K 至 6；或对高饱和/暗部区域回退全量计算 |
| 【Phase 2】实拍色卡受光线影响，批次间不一致 | 高 | 高 | 固定灯箱 + 灰卡白平衡 + 同批次拍摄；建立复测机制 |
| 10000 格渲染掉帧 | 高 | 中 | 视口裁剪 + 文字图集 + 缩放阈值，三者缺一不可 |
| MARD/COCO 色号体系本身不统一 | 中 | 高 | 先与卖家/社群核对官方色号表，建立 `color_aliases` 别名表 |

最后一条值得展开：COCO 的编号存在 `E02`、`A01`、`K39` 这类混合体系，不同卖家可能叫法不同。**建议建一张 `color_aliases` 表（color_id, alias），允许一个色号有多个可识别写法**，搜索和导入都能容错。这个表成本极低，但能省掉大量用户「搜不到色号」的投诉。

## 14. 代码仓库结构

单仓（monorepo），pnpm workspace：

```
pindou/
├── docs/                     本文档
├── packages/
│   ├── color-core/           色彩科学（纯 TS，零依赖，端 / H5 共用）
│   ├── algo/                 量化与导入算法（纯 TS，零平台 API）
│   └── shared/               类型定义、常量
├── miniprogram/              微信小程序
│   ├── core/                 小程序适配层（Canvas 读写、Worker 通信）
│   └── assets/               分包：色卡 JSON + LUT 二进制
├── scripts/
│   ├── build-lut.ts          LUT 构建（本地跑，产物提交进仓库）
│   ├── merge-colors.ts       多源色卡交叉合并
│   └── verify-colors.ts      一致性检查（散点图、离群点、跨源 ΔE）
└── data/
    ├── sources/              各来源原始数据（抓取结果，仅供比对）
    ├── mard-221.csv          合并后的数据（人工复核后定稿）
    ├── coco-291.csv
    └── sets.json             套装配置
```

**没有 `server/` 目录。** 这是有意的——零投入下不应存在任何服务端代码。

`packages/color-core` 与 `packages/algo` 是纯函数、零平台依赖。这带来两个直接好处：可以在 Node 里跑单测（不需要模拟器），以及万一小程序类目被拒，换成 H5 时算法一行不用改。

## 15. 下一步

按顺序，前三项都不写业务代码：

1. **注册个人小程序，尝试选「工具 → 图片处理」类目。** 今天就能做，半小时出结果。被拒就立刻转 H5 方案，不要继续往下走。
2. **抓色卡数据。** 见 `03` 文档，多源交叉，产出 `mard-221.csv`。
3. **搭 monorepo，实现 `color-core`，用 Sharma 的 34 组标准数据验证 ΔE00。** 这个测试过了，后面所有配色才有意义；没过，后面全是错的。
4. **命令行跑通「照片 → 图纸」**，把结果图存下来看。这是最大的技术不确定性，一天能验证。
5. **命令行跑通「像素图 → 图纸」**，验证格子识别与 1:1 还原。

**第 3 步不要跳过。** CIEDE2000 手写实现里，`hbarp` 的环绕边界和 `RT` 的符号极易写错，写错了结果只差几个 ΔE——肉眼完全看不出来，但会让所有配色系统性偏移。这是那种「上线三个月后才被用户发现」的 bug。

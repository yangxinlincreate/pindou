# 拼豆色卡数据采集规范

> 版本：v1.0
> 日期：2026-11-07
> 适用范围：MARD 221 / MARD 291 / COCO 291（首期），后续扩展 Hama / Perler / Artkal
> 责任人：需 1 人专职投入约 2 周

---

## 1. 为什么这件事值得单独写一份规范

整个产品的功能可以被抄。代码可以被抄。UI 可以被抄。

**唯独色卡数据抄不走。**

原因有三：

1. **抄来的色值本身就是错的。** 现有多数工具明确声明「HEX 来自公开资料，不是分光测色，批次有偏差」。这意味着它们的配色从一开始就建立在不准确的数据上。
2. **色值是物理测出来的，不是写出来的。** 需要买豆、搭光源、拍摄、校色、复核，是纯体力活。愿意干这件事的人少。
3. **用户会用实物验证。** 用户按你的图纸买了豆，摆完发现颜色不对，就再也不会回来。这个反馈周期是即时的，且不可挽回。

所以：**色卡准确度 = 产品生死线，不是「优化项」。**

目标很明确——**首期 MARD 221 与 COCO 291 共 512 个色号，全部做到 `confidence = measured`（实拍实测）。**

---

## 2. 数据由两部分组成，只有一部分需要自己测

这一点必须先分清，否则会做无用功：

| 数据 | 来源 | 是否需要自测 |
| --- | --- | --- |
| **色号清单**（A1、A2…B1…） | 品牌官方色卡 / 淘宝卖家图 / 拼豆社群 | 否，直接获取并核对 |
| **色号名称**（白色、浅蓝…） | 同上 | 否 |
| **色值 HEX / Lab** | **只能实拍测量** | **是，这是核心工作** |

所以工作量不在「整理色号」，而在「测 512 个颜色」。

**色号清单获取渠道（按可靠性排序）**：

1. 品牌官方色卡 PDF / 官方店客服提供的色号表
2. 淘宝头部卖家（销量 10 万+）商品详情页的色卡图
3. 小红书 / 拼豆社群的用户整理版
4. 交叉验证：至少两个来源一致才录入

**注意**：不同来源的色号清单常有缺漏或错字（尤其 COCO 的 E02 / A01 / K39 混合体系）。必须做交叉核对，形成最终清单后再开始拍摄。**清单错了，后面全白做。**

## 4. 拍摄规范

### 4.1 环境要求

| 项 | 要求 | 原因 |
| --- | --- | --- |
| 光源 | 灯箱内置 D65 灯（色温 6500K，显色指数 CRI ≥ 95） | 阳光、室内灯、手机闪光灯都会造成严重偏色 |
| 环境光 | 拉上窗帘，关闭室内顶灯 | 混光会让白平衡失效 |
| 背景 | 中性灰（18% 灰卡） | 灰背景不反射颜色，也便于后续取白平衡 |
| 距离 | 固定，镜头垂直向下 | 距离变化会改变有效光照强度 |
| 豆子排列 | 每色 20 颗，紧密平铺成 4×5 | 取平均，抵消单颗差异 |

### 4.2 拍摄方式

**每张照片的构成**：

```
┌─────────────────────────────┐
│  [灰卡]      [白纸参照]      │
│                             │
│   A1  A2  A3  A4            │
│   A5  A6  A7  A8            │  ← 每色 20 颗平铺成块
│   ...                       │
│                             │
│  [色卡编号标签]              │
└─────────────────────────────┘
```

**一次拍 20–24 个色号**，数量太少效率低，太多则单块面积小、取色不准。

**相机参数（必须手动固定）**：

| 参数 | 设置 | 说明 |
| --- | --- | --- |
| 模式 | 专业 / Pro 模式 | 关闭所有「智能优化」 |
| 格式 | RAW（DNG / ProRAW） | 保留最大调整空间；无 RAW 用最高质量 JPEG |
| ISO | 最低（通常 50 或 100） | 降噪 |
| 快门 | 自动，但需要三脚架固定 | — |
| 白平衡 | **手动 6500K**，或用灰卡自定义 | 不要用自动 |
| HDR | **关闭** | HDR 会局部提亮，破坏色值一致性 |
| 美颜 / 滤镜 / 场景识别 | **全部关闭** | 会改变颜色 |
| 对焦 | 手动锁定 | 避免每张焦点不同 |

**同一天、同一次布光、同一批参数拍完全部色号。** 中途改参数就要重拍全部。

### 4.3 拍摄中的常见坑

| 坑 | 后果 | 解法 |
| --- | --- | --- |
| 豆子正面对着光源，中心孔洞反光 | 取色时把反光当成了豆子颜色 | 光源 45° 打光，镜头垂直，避开镜面反射角 |
| 只拍单层豆子，看到侧壁阴影 | 颜色偏暗 | 平铺多层或用白色垫板抬升 |
| 透明/珠光/夜光豆混在普通豆里拍 | 曝光参数不适用 | 单独分组拍摄，单独标 `finish` |
| 一天拍不完，第二天接着拍 | 两批之间有系统性色偏 | 每天开工前先拍一张「参照组」（固定 6 个色号），用于跨批次校准 |
| 手机自动加了「鲜艳」色彩模式 | 整体饱和度偏高 | 用专业模式；或用第三方相机 App（如 Open Camera / ProCam） |

**参照组机制很重要**：固定选 6 个色号（建议 A1 白、A2 黑、一个正红、一个正蓝、一个肤色、一个中灰），每次布光后先拍这 6 个。后续比对时，如果参照组相对基准的 ΔE 超过 1.5，说明本次布光有问题，需重新调整。

## 5. 色值提取

### 5.1 处理流程

```
RAW/DNG
  │
  ├─[1] 转 TIFF（dcraw / RawTherapee，关闭所有自动调整）
  ├─[2] 灰卡取样 → 计算 RGB 增益 → 全图白平衡校正
  ├─[3] 定位每个色块区域（可用固定坐标，因为布光是固定的）
  ├─[4] 每块取中心 60% 区域，剔除高光像素（亮度 top 10%）和暗部（bottom 5%）
  ├─[5] 对剩余像素取中位数（不是均值 —— 抗异常值）
  ├─[6] 转 sRGB（D65）→ HEX
  ├─[7] 转 CIELAB
  └─[8] 输出 CSV
```

**为什么用中位数而不是均值**：豆子表面有微小高光和划痕，均值会被拉高；中位数对异常值鲁棒。

**为什么剔除高光像素**：塑料圆柱体一定有镜面高光，那部分像素的 RGB 接近 255，会把整体颜色洗淡。剔除 top 10% 亮度是必要步骤。

### 5.2 提取脚本

```python
# scripts/extract_colors.py
import numpy as np
import cv2
from colour import RGB_to_XYZ, XYZ_to_Lab  # 或自己实现，见 02 文档 §3.2

def extract_block(img_rgb: np.ndarray, x: int, y: int, w: int, h: int) -> tuple:
    """从图片中提取一个色块的代表色（中位数，剔除极端亮度）"""
    # 取中心 60% 区域，避开色块边缘的阴影和背景
    cx, cy = x + w // 2, y + h // 2
    hw, hh = int(w * 0.3), int(h * 0.3)
    patch = img_rgb[cy - hh:cy + hh, cx - hw:cx + hw].reshape(-1, 3).astype(np.float32)

    # 亮度（Rec.709）
    lum = 0.2126 * patch[:, 0] + 0.7152 * patch[:, 1] + 0.0722 * patch[:, 2]
    lo, hi = np.percentile(lum, [5, 90])
    keep = patch[(lum >= lo) & (lum <= hi)]

    if len(keep) < 50:
        raise ValueError(f'色块 ({x},{y}) 有效像素过少，检查定位')

    median = np.median(keep, axis=0)
    return tuple(int(round(c)) for c in median)


def white_balance(img_rgb: np.ndarray, gray_patch_bbox: tuple) -> np.ndarray:
    """用灰卡做白平衡校正"""
    x, y, w, h = gray_patch_bbox
    gray = extract_block(img_rgb, x, y, w, h)
    target = 128.0
    gains = [target / max(c, 1) for c in gray]
    out = img_rgb.astype(np.float32)
    for i in range(3):
        out[:, :, i] *= gains[i]
    return np.clip(out, 0, 255).astype(np.uint8)
```

**注意**：`cv2` 读图默认是 BGR，务必先转 RGB，否则红蓝通道会互换——这个 bug 出现过无数次，且很难从结果上肉眼发现。

### 5.3 输出格式

CSV（UTF-8 with BOM，便于 Excel 打开）：

```csv
code,name,hex,r,g,b,L,a,bb,finish,confidence,measured_at,batch
A1,白色,#FFFFFF,255,255,255,100.00,0.00,0.00,solid,measured,2026-11-10,B20261110
A2,黑色,#1A1A1A,26,26,26,8.65,0.01,-0.32,solid,measured,2026-11-10,B20261110
A3,正红,#E8352C,232,53,44,47.21,62.44,45.88,solid,measured,2026-11-10,B20261110
```

字段说明：
- `bb` 是 Lab 的 b 分量（避不开 b 与 rgb 的 b 冲突，导入时注意）
- `finish`：`solid` / `matte` / `pearl` / `glitter` / `translucent` / `glow` / `fluorescent`
- `batch`：拍摄批次号，格式 `B{YYYYMMDD}`

## 6. 质量验收

### 6.1 双人独立复核（必做）

| 步骤 | 做法 |
| --- | --- |
| 1 | A 完成全部提取 |
| 2 | B 随机抽取 10%（约 51 个色号）独立重新走一遍流程 |
| 3 | 计算两组的 ΔE00 |
| 4 | **ΔE00 < 1.5 视为通过**，1.5–3.0 复测，> 3.0 排查原因 |

不通过的典型原因：色块定位偏移（把背景当成了豆子）、白平衡没做、某张照片过曝。

### 6.2 分组合理性检查

把全部色号的 Lab 值画到 a-b 平面上（散点图），肉眼检查：

- 是否有明显离群点（明显偏出所在色系的）
- 同色系（如 A 系）是否沿合理方向排列

**离群点几乎一定是错的**（贴错标签、定位错误、拍到了相邻色）。这个检查成本极低，能抓出 80% 的录入错误。

### 6.3 与竞品/公开数据交叉比对

拿我们的数据与公开色卡数据（比特拼豆等）做批量对比：

- 若 > 80% 的色号 ΔE00 < 3，说明整体一致，差异在合理范围（不同批次、不同光源）
- 若某色号 ΔE00 > 8，要么我们错了，要么对方错了 —— 必须人工复测确认

**这一步的目的不是「对齐竞品」，而是「找出自己可能错的」。** 如果确认我们是对的，那就说明竞品数据确实不准，这是我们的优势。

### 6.4 实物终验（不可省略）

抽取 20 个代表性色号（覆盖白、黑、肤色、红、蓝、绿、紫、灰、透明、珠光），做完整闭环：

```
按我们记录的 HEX 在屏幕上显示色块
        ↓
打印（300 DPI，与豆子并排）
        ↓
自然光下与实物豆并排肉眼比对
        ↓
记录主观差异
```

**屏幕预览与实物必然有差异**，我们要确认的是：**差异是否在可接受范围内，且不偏向某个方向（如整体偏黄）**。系统性偏向比随机误差严重得多。

## 7. 特殊色处理

普通实色豆按标准流程走即可，以下四类需要单独处理：

### 7.1 珠光 / 金属色（pearl）

效果依赖观察角度，单一 Lab 值无法完整描述。

**处理**：记录两个角度（正面 0°、斜 45°）的色值，主色值取正面，`note` 中注明「珠光，角度不同颜色有变化」。UI 上给这类色号加角标。

### 7.2 透明 / 半透明（translucent）

颜色取决于背后的物体。

**处理**：在白色和黑色两种背景上分别拍摄，记录两个 Lab 值。产品上，透明豆在图纸中按「白底版本」配色，并加提示。

### 7.3 夜光 / 荧光（glow / fluorescent）

白天与发光状态颜色完全不同。

**处理**：只记录常光下的颜色（这才是摆豆时看到的），标注属性。不要试图记录发光状态——无法标准化。

### 7.4 亮片（glitter）

本体颜色 + 亮片颜色混合，取样中位数会偏向本体。

**处理**：接受偏差，标注 `finish = glitter`，UI 上提示「含亮片，实际观感更闪」。

**这四类色号在配色算法中的处理**：正常参与匹配，但在用量清单里加提示图标，避免用户以为是纯色。

## 8. 批次与更新机制

### 8.1 为什么会有批次差异

同一色号，不同生产批次的染料浓度会有差异，实测 ΔE00 常达 1–3。这是塑料染色工艺的固有特性，不是我们测错。

**处理方式**：

- 每次采购记录批次号
- 若某色号新批次与旧批次 ΔE00 > 2.5，更新数据并把旧值记入历史
- 界面上不暴露批次细节，但在色卡详情页注明「实测于 2026-11，不同批次可能有轻微差异」

**不要追求「唯一正确值」**——它不存在。追求的是「典型批次的准确测量」。

### 8.2 版本号规则

```
{series}-{YYYY.MM}.{序号}
例：mard-221-2026.11.1
```

- 色卡数据变更 → 版本号递增
- 端侧比对版本号，不同则重新下载
- 旧版本永久保留（用户可能还在用旧缓存）

### 8.3 用户纠错闭环

上线后开 `POST /api/v1/feedback/color` 接口，用户可提交「这个色号显示不对」。

运营侧每周汇总，超过 3 人反馈同一色号 → 重新实物复测 → 确认则更新数据 + 发版。

**这个闭环是长期优势。** 竞品的数据一旦发布就固化了，我们的会随时间越来越准。

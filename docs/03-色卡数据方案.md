# 拼豆色卡数据方案（零成本版）

> 版本：v2.0
> 日期：2026-11-07
> 前提：**前期投入 ¥0**，不买豆、不买灯箱、不买灰卡
> 范围：MARD 221（默认）、COCO 291
> 替代关系：本文档取代 v1.0 的《色卡数据采集规范》（实拍方案）。实拍方案存档在 `archive/`，等有预算时再启用。

---

## 1. 前提变了，方案就得变

v1.0 的结论是「色卡必须实拍，这是唯一的护城河」。这个结论本身没错，但它假设了有 ¥1,250 的启动预算。

现在预算是 ¥0，所以只能走另一条路：

```
实拍路线：买豆 → 灯箱 → 拍摄 → 校色 → 入库
          ¥1,250，10 个工作日，ΔE 真值误差 < 2

零元路线：公开数据 → 多源交叉 → 清洗 → 入库
          ¥0，3–4 个工作日，ΔE 真值误差 3–8（估）
```

**这不是「降级版实拍」，而是另一套完全不同的工作。** 不要用实拍的标准（双人复核、ΔE < 1.5）去要求它，那是不可能达成的。

要接受的核心事实：**首期色卡就是不够准，必须靠产品设计去消化这个不准确，而不是假装它准确。**

---

## 2. 零成本能做到什么程度

先把能力边界说清楚，避免后面预期错位。

| 能力 | 能做到 | 做不到 |
| --- | --- | --- |
| 色号清单完整（221 个 A1、A2…） | ✅ 可以，多源核对能保证不漏 | — |
| 色号名称 | ✅ 大部分有 | 少数生僻色的中文名可能缺失 |
| 色值 HEX | ✅ 能拿到 | 精度依赖来源 |
| 色值可信度 | ⚠️ 只能做「多源一致性」判断，无法验证绝对准确 | 无法验证与实物真值的偏差 |
| 特殊质感（珠光/透明/亮片） | ⚠️ 能从名称或备注推断 | 无法测角变色 |
| 批次差异 | ❌ 无法掌握 | — |

**关键判断：色值「有没有」不是问题，「准不准」才是问题。**

所以整个方案的重心不在"找数据"（数据满地都是），而在：

1. **多源交叉，剔除明显错误的值**
2. **让用户知道这个值可能不准，并给出纠错通道**
3. **用产品逻辑降低"色值不准"造成的实际伤害**

## 3. 数据从哪来

按可靠性从高到低排。

### 3.1 来源 A：官方色卡（最优，但常常没有数值）

| 品牌 | 官方渠道 | 能拿到什么 |
| --- | --- | --- |
| MARD | 官方店客服、品牌宣传物料 | 色卡图（含色号），偶尔有 PDF |
| COCO | 同上 | 色卡图 |
| Artkal | 官网有完整色卡 PDF，公开可下载 | PDF 色卡，含编号与色块 |

**做法**：拿到官方色卡图 → 直接对色块取色。比抄第三方数字更接近真实，因为图是品牌自己出的。

**注意**：色卡图如果是印刷品扫描，会有网点与偏色；如果是屏幕截图，会带 sRGB 偏差，且可能被压缩过。取色时要检查色块区域是否是纯色（方差大说明有网点/噪点）。

### 3.2 来源 B：公开色卡站点（主力来源）

这些站点公开列出了品牌色号与 HEX，可直接读取：

| 站点 | 覆盖 | 备注 |
| --- | --- | --- |
| `bitbead.pomodiary.com/zh/colors` | Perler / Hama / Artkal / MARD 221 / MARD 291 / COCO 291 / DMC | 明确标注「HEX 来自公开资料，非分光测色」——它自己承认了误差，正好 |
| `pindou.art` | 291 个色值映射 9 个品牌 | 以「色值 → 多品牌色号」的形式组织 |
| `beanpindou.com/guides/bead-color-chart` | 各品牌色数概览 | 主要用来核对色数是否对得上 |

**抓取原则（重要，别把人惹了）**：

1. 先看 `robots.txt`，`Disallow` 的路径不碰
2. 单 IP 频率压到 1 请求 / 3 秒，全套抓完约 10 分钟
3. 只提取数字（色号、HEX），不下载图片、不复制文案
4. 加一个正常的 User-Agent，不要伪装成搜索引擎
5. 数据只用于内部比对，不原样转售

**这不算"抄"，但也别理直气壮。** 色值是事实数据，不受著作权保护；但站点本身有数据库权利，低频读取、只取事实字段、注明来源，是合理边界。

### 3.3 来源 C：开源数据集（已验证可用，首选）

**更正**：本文档 v2.0 曾写「开源数据覆盖 MARD 的几乎没有」，这个判断是错的。2026-11 实测后确认，现有三个可直接使用的数据集：

| 数据集 | 覆盖 | 许可 | 实测结论 |
| --- | --- | --- | --- |
| [`makebead/craft-color-codes`](https://github.com/makebead/craft-color-codes) | 3689 色 / 15 套，含 MARD 185/221/291 | CC BY 4.0 | **首选**。JSON + CSV + npm 包，格式规整，附带 `mard-kits.json` 真实盒装配置 |
| [`pomodiary/bitbead.app`](https://github.com/pomodiary/bitbead.app) | 1406 色号 + 8436 组跨品牌 ΔE00 对照 | CC BY 4.0 | 与上者互为交叉验证源 |
| [`HansBug/pindou-color-data`](https://github.com/HansBug/pindou-color-data) | MARD 221（Alfonse + 豆豆工坊核对版） | 公开 | 第三份独立来源，可用于三方比对 |

**这批数据的性质要说清楚**：`status: community` —— 是社区从产品图和商家色卡采样的，**不是色差仪实测**。上游来源为 peiseka.com、pixel-beads.com 等。这和我们自己抄公开资料是同一量级，但它有三个好处：格式规范、有明确许可、有第三方在用（错了会被发现）。

**已实测的关键数据**：

```
MARD 221：221 色，色系分布 A26 B32 C29 D26 E24 F25 G21 H23 M15
盒装套装：24 / 48 / 72 / 96 / 120 / 144 / 168 / 192 / 216 / 221
          （每组是「前一组 + 固定色块」，来自厂家套装卡转录）
```

**套装数据是意外之喜。** 这份 `mard-kits.json` 直接给出每个零售盒装包含哪些色号，正好补上了本项目一直缺的「按我的套装生成」能力的数据底座。自己整理这份数据需要买齐 10 个盒子，约 ¥2000。

**覆盖度实测**（随机 2000 个 sRGB 颜色到最近色号的 ΔE00）：

| 色卡 | P50 | P90 | 说明 |
| --- | --- | --- | --- |
| 自建合成色卡 | 4.09 | 6.67 | 按 Lab 均匀采样，覆盖最理想 |
| 真实 MARD 221 | 5.57 | 9.35 | 真实色卡分布不均，某些区域确实没有色 |

**P90 = 9.35 不是数据错误，是真实色卡的客观属性。** MARD 221 在部分高饱和、深色区域确实没有合适色号（Bitbead 也提到，高饱和青色往 Hama 转时最近色差到 ΔE 17.8）。这意味着：**有些颜色用户是真的买不到**，产品必须披露，而不是假装能配准。

**许可合规**：CC BY 4.0 允许商用，但**必须署名**。已在两处落地：
- 小程序「我的」页底部
- Web 验证台左侧面板底部

### 3.4 来源 D：卖家详情页实拍图（弱证据，用于发现异常）

淘宝 / 1688 商品详情页常有一张"全色号色卡实拍图"。

**不要用它做主要数据源**（光线、白平衡、压缩全都不可控），但**可以用来抓"离谱值"**：某色号在多源里是"浅粉"，实拍图上明显是"深红"，说明抄错了。

人工抽查 20–30 个可疑色号即可，不要全量处理。

### 3.5 来源 E：社群整理文档

小红书、飞书/石墨公开文档里有爱好者整理的色号表。**通常只有色号没有 HEX**，适合用来补全清单、核对名称，不适合取色值。

## 4. 多源交叉：具体怎么做

### 4.1 步骤

```
Step 1  每个来源单独存一份 CSV（不改动，原样保存）
   ↓
Step 2  以「色号」为主键对齐（A1、A2…），不是以名称对齐
   ↓
Step 3  逐色号计算各来源两两之间的 ΔE00
   ↓
Step 4  按一致性分级（见下表）
   ↓
Step 5  分级处理 → 产出定稿 CSV
```

### 4.2 一致性分级与处理

| 分级 | 判据 | 处理 | 预期占比 |
| --- | --- | --- | --- |
| A 一致 | 所有来源两两 ΔE00 < 2 | 直接取中位数 | 60–75% |
| B 轻微分歧 | 最大 ΔE00 在 2–5 | 取中位数，标记 `confidence = 'medium'` | 15–25% |
| C 明显分歧 | 最大 ΔE00 在 5–12 | 人工看实拍图裁决，标记 `confidence = 'low'` | 5–10% |
| D 冲突 | 最大 ΔE00 > 12 | 大概率某源抄错了色号。人工裁决；无法判断则取来源 A（官方） | < 5% |

**取中位数而不是平均值**：三个来源里如果有一个错得离谱，平均值会被拖偏，中位数不会。

### 4.3 一个必须知道的局限

多个公开站点很可能**抄的是同一份原始数据**。它们的 ΔE 高度一致，不代表准确，只代表同源。

所以：**多源一致性只能排除"抄错色号"这类错误，不能验证色值是否接近实物。**

这个局限没法在零成本下解决。唯一能做的是承认它，并在产品上做好披露。

## 5. 数据清洗规则

公开数据脏在三个地方，逐条处理：

### 5.1 色号格式不统一

| 脏数据 | 规范化为 |
| --- | --- |
| `a1` / `A1` / `a-1` / `A 1` | `A1` |
| `COCO E02` / `E-02` / `E2` | `E02`（补齐两位） |
| `MARD-A1` / `MARD A1` | `A1`（brand 单独存字段） |
| `#FFF` / `fff` / `#ffffff` / `rgb(255,255,255)` | `#FFFFFF` |

**必须建别名表**（`color_aliases`）：同一个色号的不同写法都映射到标准 ID。这个表成本极低，但能省掉大量"搜不到色号"的投诉。

### 5.2 明显错误的值

自动过滤以下情况：

| 规则 | 原因 |
| --- | --- |
| HEX 全为 `#000000` 或 `#FFFFFF` 的色号 > 3 个 | 大概率是占位符没填 |
| 同一系列内两个色号 HEX 完全相同 | 抄漏了 |
| Lab 的 L < 5 却命名为"白色" | 名称与色值矛盾 |
| 色号总数与官方色数不符 | 清单缺漏 |

### 5.3 缺失值

- 缺 HEX 但有名称 → 用名称做人工估色（不推荐，只在极端情况用）
- 缺名称但有 HEX → 留空，界面只显示色号
- 缺色号但有 HEX → **直接丢弃**，无主的数据没用

## 6. 验收

零成本没有"双人复核"的条件，改用**脚本自动检查 + 人工看散点图**。

### 6.1 自动检查（脚本跑，10 秒出结果）

| 检查项 | 通过标准 |
| --- | --- |
| 色号数量 | = 官方公布色数（MARD 221 就是 221 个） |
| 色号无重复 | 0 重复 |
| HEX 格式合法 | 100% |
| HEX 无重复（同系列） | 0 重复 |
| Lab 转换往返误差 | RGB→Lab→RGB 误差 ≤ 1 |
| 多源覆盖率 | 每个色号至少 2 个来源 |

### 6.2 人工看散点图（5 分钟）

把 221 个色的 Lab a-b 值画成散点图，按色系（A/B/C…）上色。

- 每个色系应该聚成一簇
- 出现远离本簇的孤立点 → 一定是错的（贴错标签、抄错行）
- 整簇偏移 → 该色系可能来自不同来源，需统一

**这一步成本极低，能抓出 80% 的录入错误。** 强烈建议每批数据都做一次。

### 6.3 抽检实拍图（30 分钟）

随机抽 20 个色号，去淘宝详情页找到对应色卡实拍图，肉眼比对：

- 我们的 HEX 显示的颜色 vs 实拍图上的颜色
- 只要"大致是同一个颜色族"就算通过（不要求精确）
- 出现"我们说是浅蓝，实拍是深蓝"这种 → 严重错误，全量复查

## 7. 众包校准（长期，这是唯一能提升精度的路）

零成本不代表无法改进。**用用户的眼睛当免费的测量仪。**

### 7.1 通道设计

首期没有后端，只有一条通道：**微信客服会话**。

```html
<button open-type="contact"
        show-message-card="{{true}}"
        send-message-title="色号纠错：{{code}}"
        send-message-path="pages/palette/detail?code={{code}}">
  这个颜色不对
</button>
```

用户点进去，自动带上色号，他可以发文字、发实物照片。你在微信公众平台的客服后台直接收到。

**零开发、零成本、零服务器。** 而且比表单好用——用户拍了实物发过来，信息量大得多。

### 7.2 放在哪里（决定收集效率）

| 位置 | 转化率 | 说明 |
| --- | --- | --- |
| 色号详情页 | 中 | 用户主动查色时 |
| **导出成功后的提示** | **最高** | 用户刚看完图纸，印象最深 |
| 用量清单底部 | 高 | 用户准备下单时最容易发现问题 |
| 关于页 | 低 | 兜底 |

**别放在设置里。** 没人会去那里找反馈入口。

### 7.3 收到反馈后怎么处理

```
用户反馈「A12 应该是深一点的蓝」
   ↓
累计同一色号 ≥ 3 条独立反馈
   ↓
人工去淘宝实拍图核对
   ↓
修正 HEX → 更新 CSV → 重新构建 LUT → 发版
```

发版频率低没关系（色卡几个月才变一次），但**每一条反馈都要回**。回复本身就是留存手段。

### 7.4 一个零成本的巧思

用户发来的实物照片，本身就是一次"实拍采样"。虽然光线不可控，但如果你收集到同一色号的多张不同光线照片，取它们的中位数，精度会明显好于抄来的数据。

**这就是零成本的实拍数据来源**——只是采集者是用户，不是你。

可以在客服回复里引导：「方便的话拍一张自然光下的照片发我，我核对后更新数据」。愿意配合的用户不多，但 5% 就够了。

## 8. 精度不够，产品上怎么补

色值不准是既成事实。别指望用户察觉不到，要在产品层面主动化解。

### 8.1 诚实披露（不是免责声明，是功能）

色号详情页底部固定一行小字：

> 色值为公开资料整理，与实物可能存在差异。大批量购买前建议先看商家实物色卡。

「关于」页写清楚数据来源与局限。

**这句话会劝退一部分用户吗？会。** 但它同时会让留下的用户更信任你——因为竞品不说。

### 8.2 用配色策略规避高风险色

不同色系的色值误差，造成的实际伤害差别很大：

| 色系 | 误差敏感度 | 说明 |
| --- | --- | --- |
| 鲜艳色（正红、正蓝、亮黄） | 低 | 色号间距大，错一点也能看出来该选哪个 |
| 肤色 / 浅粉 / 米色 | **高** | 相邻色号 ΔE 很小，色值偏差会直接选错 |
| 灰阶 | **高** | 同一支灰有 5 个色号，差一点就跳号 |
| 深色（黑、深蓝） | 中 | 屏幕上难分辨，但实物差异也小 |

**产品对策**：

1. 肤色区域用「稳妥色」——不选色卡两端的极端值，选中间档
2. 用量清单里，对 `confidence = 'low'` 的色号加一个小标记「建议核对实物」
3. 不提供「一键跨品牌替换」功能（首期本来也不做），避免误差被二次放大

### 8.3 不承诺的话术

**绝对不要写**：「精准配色」「与实物一致」「专业级色准」。

**可以写**：「按真实色号配色」「可直接下单」「色值仅供参考」。

这条底线守不住，后面全是投诉。

## 9. 什么时候值得花钱（升级路径）

零成本是起点，不是终点。设定明确的升级触发条件，别凭感觉。

| 触发条件 | 动作 | 成本 |
| --- | --- | --- |
| 累计 1,000 用户，且收到 ≥ 30 条色号纠错 | 买 MARD 221 套装 + 灰卡，做一轮实拍校准 | ¥400 |
| 日活稳定 > 500，或开始有会员收入 | 完整实拍（灯箱 + ColorChecker + 双人复核） | ¥1,900 |
| 用户开始批量采购（B 端询单） | 实拍 + 批次跟踪 | ¥2,500+ |

**最先投入的永远是最高频的色号**，不是全量。肤色、黑白灰、常用红蓝绿，这 30 个色号覆盖了 80% 的用量。先校准这 30 个，投入不到 ¥100（买散装豆），收益最大。

**这个顺序很重要**：不要等"有钱了做全量实拍"，而是"有 100 块了先校准 30 个高频色"。

## 12. 最后一句实话

这份方案产出的色卡，**精度一定不如实拍**。用户按图买豆，可能出现轻微色差。

这不影响产品能成立——用户要的是「能从我的照片得到一份可下单的清单」，而不是「像素级色彩还原」。竞品的色值同样来自公开资料，大家在同一起跑线上。

真正的差距会在两个地方拉开：

1. **谁的纠错通道更通畅**（用户愿意告诉你哪里错了）
2. **谁更早把纠错沉淀成数据**（收到就改，还是收完就忘）

第 1 条靠产品设计，第 2 条靠运营纪律。这两件事都不花钱，但都需要持续做。
